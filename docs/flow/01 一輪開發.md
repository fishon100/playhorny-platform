# 01 一輪開發

> 總覽：[00 總覽](00%20總覽.md)。整套流程的主線：**想法 → 提案 → 同意 → 實作 → 上線 → 試玩 → 驗收**。
>
> **企劃正在跟 AI 對話時，用「對話一條龍」**：說需求 → AI 寫提案，直接在對話裡跳出「需要企劃確認的事」的選項 → 你點選、按「同意」→ AI 直接做到上線 → 你試玩後說「X 驗收通過」。整個過程**不用打開管理台**；管理台只用來看進度，或給不在對話裡的人（主管、其他企劃）同意。

## 流程圖

```
 ① 想法                 ② 討論（選用）       ③ 提案               ④ 企劃同意（任一個入口）
 工作台「提需求」 ─────▶ /spectra-discuss ─▶ /spectra-propose ─▶ 工作台／GitHub Issue 勾 ☐ 企劃同意
 （或 Notion 需求池）                          自動開提案 Issue     Notion 卡改「同意」・桌面版勾 0.1・跟 AI 說
                                                                       │ 自動：任務 0.1 打勾
 ⑧ 驗收                  ⑦ 試玩回饋            ⑥ 上線通知             ⑤ 實作（TDD）
 /spectra-archive ◀───── 工作台「寫回饋」 ◀─── 部署＋手機通知 ◀───── /spectra-apply
   │ 自動：提案 Issue 關閉     │ 有 🔴 → 回到 ⑤（/spectra-ingest 把新要求併進提案）
   └─ 規則併回規則書、寫開發日誌
```

## 每一步誰做、在哪裡、做什麼

| 步驟 | 誰 | 在哪裡 | 做什麼 | 對 AI 說 |
|---|---|---|---|---|
| ① 想法 | 任何人 | 工作台「💡 提需求」（＝GitHub Issue 表單）；有 Notion 的專案也可以寫 Notion 需求池 | 寫：玩家遇到什麼、想要什麼感覺、參考 | — |
| ② 討論 | 企劃＋AI | Claude Code | 需求還模糊時，先比較做法，不改程式 | 「討論 <需求>」 |
| ③ 提案 | AI | GitHub `docs/spectra/changes/<名稱>/` | 寫提案（見下）；推上去後 **GitHub 自動開一個「提案」Issue**，工作台首頁出現「等你同意」 | 「看需求」「把 <需求> 開成提案」 |
| ④ 同意 | 企劃 | 見下面「四種同意方式」 | 讀為什麼、改什麼、**需要企劃確認的事**；同意或留言 | — |
| ⑤ 實作 | AI | GitHub | 確認任務 0.1 已勾 → 先寫會失敗的測試 → 寫程式 → 測試全過；任務逐項打勾 | 「做 <名稱>」 |
| ⑥ 上線 | AI＋GitHub Actions | 自動 | 推上 GitHub → 測試 → 部署預覽網址 → 手機通知 | （⑤ 做完自動） |
| ⑦ 試玩 | 企劃（＋美術） | 手機 | 打開預覽試玩，工作台「🎮 寫回饋」（🔴🟡🟢） | 「看回饋」 |
| ⑧ 驗收 | 企劃說 OK → AI | GitHub | 規則併回規則書、提案搬到 archive、寫開發日誌；**Issue 自動關閉** | 「<名稱> 驗收通過」 |

## 四種同意方式（都算數，挑最方便的）

正本只有一個：提案 `tasks.md` 的第一項 **`- [ ] 0.1 企劃確認`**。AI 動工前只看它。

| 在哪裡 | 怎麼做 | 怎麼變成「0.1 已勾」 | 適合 |
|---|---|---|---|
| **工作台 → GitHub Issue** | 首頁「看內容並同意」→ 勾 **☐ 企劃同意** | GitHub Actions 約 1 分鐘內自動勾 0.1，註明「企劃於 GitHub Issue #N 同意，日期」，並在 Issue 回覆確認 | **手機、任何電腦**（推薦） |
| Notion | 「提案確認」卡片狀態改「同意」 | 對 AI 說「看提案」，AI 讀 Notion 後勾 0.1 並註明來源 | 有用 Notion 的團隊 |
| Spectra 桌面版 | 打開提案的 tasks → 勾 0.1 | 直接就是正本；記得推上 GitHub（或對 AI 說「推上去」） | 在電腦前看細節 |
| 跟 AI 說 | 「同意 <名稱>」 | AI 勾 0.1，註明「企劃於對話中同意」 | 正在跟 AI 討論的時候 |

**有意見、要修改**：在提案 Issue（或 Notion 卡片）留言，再對 AI 說「看提案」，AI 會照意見改提案、在 Issue 回覆改了什麼。

## 提案的文件（企劃要看懂的部分）

| 檔案 | 寫什麼 | 企劃要看嗎 |
|---|---|---|
| `proposal.md` | 中文標題、**為什麼**要改、**改什麼**、BREAKING、**需要企劃確認的事** | ✅ 一定要看（Issue 內文就是它的摘要） |
| `specs/<功能>/spec.md` | 改了哪幾條**規則**，每條附「情境：當…則…」 | ✅ 看規則有沒有寫錯 |
| `design.md` | 程式**怎麼做**、為什麼選這個做法 | 選看（程式審查看） |
| `tasks.md` | 0.1 企劃確認＋待辦清單，做完一項勾一項（工作台的進度條就是它） | 選看 |

> 規則書（`docs/spectra/specs/`）＝遊戲「現在」的規則。提案＝「想要改成什麼」。驗收時提案裡的規則會併回規則書。

## 狀態（工作台上看到的）

| 狀態 | 意思 | 下一步誰 |
|---|---|---|
| 待同意 | 提案寫好了，0.1 還沒勾 | 企劃 |
| 已同意 | 0.1 已勾，還沒開始做 | AI（「做 <名稱>」） |
| 製作中 | 任務做到一半 | AI |
| 待驗收 | 任務都做完、已上線 | 企劃試玩 → 說「<名稱> 驗收通過」 |
| 已完成 | 規則併回規則書 | — |

## 什麼時候不用開提案

- **不改規則**的小事（錯字、顏色、明確的 bug）：直接說「修 <問題>」，AI 修好、跑測試、部署，在開發日誌記一筆。
- 試玩發現的 bug：AI 用 `/spectra-debug` 先重現、找原因；修法如果改到規則，還是要開提案。

## 做到一半需求變了

不要另開新的。對 AI 說「<名稱> 改成 …」，AI 用 `/spectra-ingest` 把新要求寫回同一張提案，**把 0.1 取消勾選**，請企劃再同意一次（Issue 會重新出現在「等你處理」）。

## 品質關卡（AI 自己會跑，驗收前一定過）

| 指令 | 檢查什麼 |
|---|---|
| `/spectra-analyze` | 提案文件之間有沒有矛盾、漏掉 |
| `/spectra-verify` | 程式是不是真的照規則、任務、設計做了 |
| `/spectra-review` | 程式審查（只出報告，不改檔）；程式審查員看這份 |
| `/spectra-drift` | 提案寫的和現在的程式有沒有對不上 |
